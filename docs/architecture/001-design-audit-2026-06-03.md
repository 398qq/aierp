# AIERP 架构设计评估

**日期**：2026-06-03
**作者**：架构评估
**目的**：盘点 AIERP 前后端设计的真实状态，识别结构性技术债，排出可执行的收尾路线
**状态**：评估报告，不改代码

---

## 0. TL;DR

| 维度 | 评估 |
|---|---|
| 后端架构分层 | 名存实亡。"DDD 4 层"（`app/domain`、`app/application`、`app/infrastructure`、`app/services`）已建，但 90% 业务代码仍堆在 `app/services/`（17,706 行）和 `app/api/v1/`（14,998 行）。`domain/` + `application/` + `infrastructure/` 合计 3,551 行（10%）。 |
| 后端 API 单文件巨型化 | 严重。`sales.py` 952 行、`transactions.py` 623 行、`finance.py` 542 行、单一文件 200-500 行 是常态。 |
| 后端双套路由 | `sales.py`（legacy）+ `sales_v2.py`（演示新架构）并存，未合并。`sales_v2.py` 自己就是"理想架构"的活样板，但只覆盖 3 个用例。 |
| 前端 App.tsx 路由表墙 | 严重。`App.tsx` 内联 60+ `lazy()` + `<Route>`，无嵌套布局，无 feature 分组。 |
| 前端 API 客户端巨型 | 严重。`src/api/index.ts` 1,184 行单文件，覆盖 18 个业务域。 |
| 前端共享组件 | 缺失。`components/` 只有 1 个通用组件 + 2 个子目录，每个页面重复实现 `StatusTag`、`MetricBand` 等模式。 |
| 状态管理 | `store/` 只有一个 `auth.ts`，业务状态散在组件里。 |
| 类型安全 | 后端 24 个 mypy 错误（含 5 个 `event_bus` 类型问题、5 个 `inventory_repo.rowcount`），前端 `tsc --noEmit` 此前能过但无 zod/runtime 校验。 |
| 测试覆盖 | 815 通过 / 5 失败（pre-existing，与 v5 无关）。新增 `test_cache_finance_reports.py`（23 个）+ `test_date_format.py`（12 个）覆盖率清晰。 |

**核心结论**：性能优化（v3→v5）只治了"性能症状"，没治"架构病根"。继续在巨型文件上做战术优化，会越改越难——必须先把架构分层坐实，再谈别的。

## 1. 后端：当前架构 vs 目标架构

### 1.1 目标架构（已存在于骨架代码）

`app/` 目录里已经有完整的 DDD 4 层目录：

```
app/
├── domain/           # 实体、值对象、领域事件、聚合根（零外部依赖）
│   ├── finance/      # 账期、凭证
│   ├── inventory/    # 批次、成本策略
│   ├── procurement/  # 三方匹配
│   ├── sales/        # 报价单、发货单
│   └── shared/       # 共享：money、errors、events
├── application/      # 用例（编排 domain）、UoW、事件处理器
│   ├── sales/        # confirm_order / cancel_order / convert_quotation
│   ├── procurement/  # three_way_match
│   ├── uow.py
│   └── event_handlers.py
├── infrastructure/   # 仓储、缓存、外部服务适配
│   └── persistence/inventory_repo.py
├── services/         # ？？？（实际：老的服务层 + AI 编排）
├── api/v1/           # ？？？（实际：所有 HTTP 入口 + 业务逻辑）
├── core/             # 横切：permissions / security / observability
├── models/           # SQLAlchemy ORM
└── schemas/          # Pydantic 请求/响应
```

### 1.2 实际代码分布（残酷事实）

| 层 | 文件数 | 代码行数 | 占总业务代码 | 业务逻辑真实位置 |
|---|---|---|---|---|
| `app/api/v1/` | 28 | **14,998** | **44%** | 大量业务逻辑直接写在这里（见 §1.3） |
| `app/services/` | 28 | **17,706** | **51%** | 大部分是"service"命名的老逻辑 + AI 编排 |
| `app/application/` | 6 | 835 | 2% | 4 个 use case，几乎没被 router 用 |
| `app/domain/` | 15 | 2,427 | 7% | 实体定义、领域事件，但没被业务代码用 |
| `app/infrastructure/` | 3 | 289 | 1% | 只有 inventory_repo.py |

**新架构的代码占比 10%。** 旧的"services+api"双层 95%。

### 1.3 API 层巨型单文件

`app/api/v1/` 里这些文件本身就是"业务逻辑"而不只是"HTTP 适配"：

| 文件 | 行数 | 业务逻辑类型 |
|---|---|---|
| `sales.py` | **952** | 商机、报价、订单、发货单、发票、付款 — 6 个聚合全在这 |
| `transactions.py` | 623 | 采购单全流程 |
| `finance.py` | 542 | 发票、付款、合同、目标 |
| `finance_accounts.py` | 497 | 会计科目、凭证、银行对账、P&L、AP |
| `dashboard.py` | 404 | 仪表板全套 |
| `reports.py` | 418 | 报表 + 模板 + 导出 |
| `approvals.py` | 384 | 审批流 |
| `sales_v2.py` | 232 | 演示新架构的"样板间" |

每个文件里都直接做 `select(Invoice).where(...)`、`compute aggregates`、调用 `cache_bump_version`、写 `raise fail(...)` — 这是业务逻辑，不是适配器。

**正确分层**应当是：HTTP 入口 50-100 行做参数校验和响应包装，业务逻辑下沉到 `application/use_cases/` 或 `domain/aggregates/`。

### 1.4 sales_v2.py 是活样板但没落地

`app/api/v1/sales_v2.py:1-50` 的模块 docstring 自述：

> "This router demonstrates the new architecture:
> - Thin HTTP adapters (validate input, return response)
> - All business logic in use cases
> - Explicit UoW dependency for transaction boundaries
> - Domain events tracked on the UoW for after-commit dispatch"

—— 这是**理想**架构。但只覆盖了 3 个用例（confirm / cancel / convert_quotation），命名在 `/sales-v2/*` 隔离主路由，**没有**迁移主路由。`sales.py` 还在加新功能（如 v5 加的 `reports:predefined:sales` 失效）。

**两个 router 并存的问题**：
- 后续维护不知道该往哪边加
- "新架构"长期停留在演示阶段
- 没合并就永远没合并

### 1.5 13 个 `_intel_service.py` + AI 编排层

`app/services/` 下有 13 个 `*_intel_service.py`（brand / supplier / product / customer / target / ticket / visit / contract / finance / po / nlp / orchestration / sales_ai_pipeline），单文件 290-1,089 行。`sales_ai_pipeline.py`、`nlp_query_service.py`、`orchestration/global_orchestrator.py` 是 3 个 AI 编排器，职责重叠且无清晰边界。

这不是 DDD 意义上的"domain service"——这是"按业务对象 × AI 能力 × × 切片"的爆炸。如果 AI 编排要继续投入，建议至少分清：
- 触发层（事件订阅 / 写后钩子）
- 编排层（决定用哪些 AI agent / 工具）
- 执行层（实际调 LLM）

现在三个全混在 1,000 行单文件里。

## 2. 前端：当前架构 vs 目标架构

### 2.1 当前结构（数字说话）

```
src/
├── App.tsx              # 200+ 行：60+ lazy + <Route> + 业务重定向逻辑
├── main.tsx
├── api/
│   ├── client.ts        # 103 行（axios 封装）
│   └── index.ts         # 1,184 行：18 个业务域的 API 调用
├── components/          # 1 个通用组件 + 2 个子目录
│   ├── AttachmentPanel.tsx
│   ├── ai/
│   └── sales/
├── layouts/
│   └── MainLayout.tsx
├── pages/               # 18 个子目录，60+ 页面
├── store/
│   └── auth.ts          # 36 行：唯一 Zustand store
├── types/               # 100+ 类型，跨 18 业务域混在一起
└── test/                # 4 个测试文件
```

**核心数字**：
- `api/index.ts` 1,184 行（占前端业务代码 25%）
- `App.tsx` 路由表 200+ 行
- `pages/sales/salesUi.tsx` 785 行（单文件多职责）
- 共享组件 = 1 个

### 2.2 App.tsx 是"路由表墙"

60+ 个 `lazy(() => import(...))` + 60+ 个 `<Route>`，全是顶层平铺：

```tsx
const Dashboard = lazy(() => import("./pages/dashboard/index"));
const CustomerList = lazy(() => import("./pages/customers/index"));
const CustomerDetail = lazy(() => import("./pages/customers/CustomerDetail"));
// ... 60+ 行
const SalesOrderDetail = lazy(() => import("./pages/sales/SalesOrderDetail"));
// ...

function App() {
  return (
    <Routes>
      <Route path="/login" element={<Login/>} />
      <Route element={<MainLayout/>}>
        <Route path="/" element={<Dashboard/>} />
        <Route path="/customers" element={<CustomerList/>} />
        <Route path="/customers/:id" element={<CustomerDetail/>} />
        // ... 60+ 行
      </Route>
    </Routes>
  );
}
```

**问题**：
- 60+ 路由无嵌套布局（按业务聚合分组）
- 新增页面要改 App.tsx + 同时改 `pages/` + `api/index.ts`，跨 3 个文件
- 不知道哪些路由已废弃、哪些是新加的
- 路由元信息（图标、面包屑、权限）散在侧边栏代码里，App.tsx 不管

### 2.3 `api/index.ts` 是"扁平 API 集合"

1,184 行单文件，14+ 业务域混编：Auth / Users / Customers / Products / Suppliers / Brands / Inventory / Sales / Procurement / Finance / Reports / Tickets / Warehouse / Public。

```ts
// 顶部类型 import
import type { Customer, Product, Quotation, ... 100+ types } from "../types";

// 然后是 200+ 扁平的 export const xxx = (params) => client.get(...)
```

**问题**：
- 加 endpoint → 加 export → 文件越长
- 没有 endpoint → service 映射，业务方引用 `getCustomer(id)` 时不知道背后调了 `/customers/{id}` 还是 `/customers/{id}/detail`
- 重构 service 调用方式（如加 retry/circuit breaker）需要全局替换
- 命名冲突风险（不同业务域都有 `getStats`）

### 2.4 没有共享 UI 组件库

每个页面重复实现：
- `StatusTag`（订单状态、发票状态、付款状态）— 至少出现 8 次（grep 估计）
- `MetricBand`（KPI 卡）— 至少 5 次
- `SearchBar` / `FilterBar` — 模式相似但实现不同
- `PageHeader` / `Breadcrumb` — 部分页面有，部分没有

`components/` 几乎为空，是这个 60+ 页面的应用里最显眼的反常。

### 2.5 `pages/sales/salesUi.tsx` 785 行的危害

这是单个"销售 UI 工具"文件。看似 785 行不算巨，但耦合在多个页面中（grep 一下有 ~10 个 import 来自 `salesUi`）。这种"公共 UI 工具"模式：

- 改一处要担心影响 10 个页面
- 没有人愿意做完整的 type refactor
- 测试覆盖近乎 0（grep `salesUi` 在 test 目录里 0 命中）

## 3. 横切关注点

### 3.1 类型安全

- **后端 24 个 mypy 错误**（5 类）：
  - `app/core/event_bus.py:62-64` — `dict[type, list[Callable]]` 索引 type 字段为 `type | None`（事件订阅没强制传 type）
  - `app/infrastructure/persistence/inventory_repo.py:94,138,191,266` — `Result.rowcount` 不存在（SQLAlchemy 2.x API 错误）
  - `app/application/event_handlers.py:36-87` — `EventBus.subscribe()` 期望 `type` 实际收到 `Callable`
  - `app/services/ai/agent_modules/embedding.py:146,182` — `where` 谓词类型不对
  - `app/services/pdf_service.py:212,332,443,519` — `Decimal | Literal[0]` 返回类型不一致
  - `app/api/deps.py:51` — async generator return type 注解
  - `app/api/v1/finance.py:445` — `ct.get("id")` 应该是 `ct.id`（已在 v5.1 修复）

  **5/24 在新架构层（`domain` / `application` / `core/event_bus`），是新架构没落地的直接证据。**

- **前端**：现在 `tsc --noEmit` 通过，但 `api/index.ts` 里 200+ 调用都是 `client.get<APIResponse<PageData<Record<string, unknown>>>>` 这种——**大量使用 `Record<string, unknown>` 逃避类型**。这不是 type-safe，是 type-disabled。

### 3.2 测试覆盖空白

815 个测试看似不少，但分布严重不均：

| 层 | 测试 | 备注 |
|---|---|---|
| API 集成测试 | 多 | 5 个 test_*.py 覆盖 18 个 endpoint family |
| 缓存测试 | 23 | v5 新增 |
| 单元测试 | 少 | `test_money.py`、`test_cost_strategy.py`、`test_inventory_batch.py` 等 |
| **Domain 单元测试** | **0** | `app/domain/` 没有 `test_*.py` |
| **Use case 单元测试** | **少量** | 3 个 use case 中只有 `test_convert_quotation_use_case.py` 一个 |
| **E2E / Playwright** | **0** | 后端集成测试覆盖到了，但前端用户流程没自动化 |

### 3.3 文档缺口

- 没有 `docs/architecture/` 目录（本次创建）
- 没有 ADR（架构决策记录）
- 没有 API 契约文档（OpenAPI 由 FastAPI 自动生成但未维护）
- 前端组件库没有 Storybook / 文档
- `docs/progress.md` 是成就清单，不是设计参考

### 3.4 性能 — 已基本解决

v3-v5 三轮优化已建立 18 个 cache family、4 worker gunicorn、Alembic 索引、慢查询日志。性能已不是 P0，但还有：
- 跨 worker 缓存失效（v5 报告 P3）
- 缓存预热（v5 报告 P3）
- 23 个 mypy 错误（与性能无关，但卡 lint CI）

## 5. 收尾路线图

### 阶段 1：拆巨型文件 + 合并双路由（1-2 周）

**目标**：消灭"动一处怕影响全局"的最大障碍。

**5 个原子任务**：

1. **`app/api/v1/sales.py` 拆 6 个子包**
   `app/api/v1/sales/{opportunity,quotation,order,delivery,invoice,payment,contract,target,purchase_order}.py` + 共享 `deps.py`
   - 路由拆分按 bounded context
   - 业务逻辑下沉到 `application/sales/{context}_use_case.py`
   - `sales_v2.py` 的 3 个 use case 合并回主包
   - 删除 `/sales-v2/*` 路由前缀

2. **`app/api/v1/finance.py` 拆 invoices / payments / contracts / targets**
3. **`app/api/v1/finance_accounts.py` 拆 accounts / journal / bank / reports.pnl / reports.ap**
4. **`app/api/v1/reports.py` 拆 templates / predefined/{sales,ar,inventory,procurement} / export**
5. **`app/api/v1/transactions.py` 拆 po（采购）— 这是 sales 不该管的**

**前端**：

6. **拆 `src/api/index.ts` 按业务域**
   `src/api/{auth,users,customers,products,suppliers,brands,inventory,sales,procurement,finance,reports,public,...}.ts` + `index.ts` 仅 re-export

7. **App.tsx 嵌套布局 + 路由配置外提**
   - `src/routes/{public,protected}.tsx`
   - `src/routes/registry.tsx`（路由元信息：icon、permission、breadcrumb）
   - App.tsx 缩减到 ~30 行

**验证**：
- 所有现有测试 0 修改通过
- `grep` 检查没遗漏的 `from .sales import`（跨子包）
- bundle 体积不变（拆分只是逻辑组织，不影响 chunk 切分）

### 阶段 2：DDD 落地 + 共享 UI（2-3 周）

**目标**：让"新架构"从 10% 扩到 50%+。

**5 个原子任务**：

1. **Domain 单元测试补齐**：`app/domain/{finance,sales,inventory,procurement,shared}/` 下的实体各加 5-10 个 unit test
2. **Use case 覆盖**：所有 `application/*/use_case.py` 加单元测试
3. **前端共享 UI 组件库 v1**：`src/ui/{StatusTag,MetricBand,SearchBar,PageHeader,Breadcrumb,EmptyState,ErrorBoundary}.tsx`
4. **替换高频复用组件**：所有 `pages/sales/*`、`pages/customers/*` 里手写的 StatusTag 替换为 `<StatusTag type={...}>`
5. **AI 编排分层**：拆 `nlp_query_service.py`（1,089 行）和 `sales_ai_pipeline.py`（537 行），分触发 / 编排 / 执行三层

**验证**：
- `pytest --cov=app/domain --cov=app/application` 覆盖率 ≥ 80%
- 前端 bundle 拆分到 `pages/feature/Page.tsx` 后，每个 chunk < 300 KB

### 阶段 3：类型安全 + ADR + 跨 worker 缓存（2-3 周）

1. **后端 mypy 0 错误**：先按 5 类逐类修（event_bus 类型、inventory_repo、event_handlers、embedding、pdf_service、deps.py）
2. **前端 zod 校验 + 替代 `Record<string, unknown>`**：所有 `api/*.ts` 的 response 类型用 zod schema 生成
3. **ADR**：在 `docs/architecture/adr/` 写 5-10 个关键决策（缓存策略、DDD 边界、AI 编排分层等）
4. **跨 worker 缓存失效**（P3 from v5 报告）：Redis Pub/Sub 广播 `cache_bump_version` 事件，其他 worker 收到后 L1 epoch bump
5. **前端 E2E（Playwright）**：3-5 个核心用户流程

## 6. 关键决策（需要用户回答）

在我动手前有几个方向性选择需要你拍板：

### 6.1 阶段 1 拆分 API 时，**业务逻辑放哪**？

当前业务逻辑一半在 `app/api/v1/*.py`（直接做 SQL 查询 + 业务规则），一半在 `app/services/*.py`。

**3 个选项**：

A. **沿用 services 模式**：把 `sales.py` 里的业务逻辑搬到 `app/services/sales/{opportunity,quotation,...}.py`，API 文件瘦到 50-100 行只做适配
   - 改动最小
   - 但 DDD 永远落不了地

B. **走 use case 路线**：业务逻辑搬到 `app/application/sales/{opportunity,quotation,...}_use_case.py`，用 `app/application/uow.py` 管事务边界
   - 改动较大（~30 个 endpoint）
   - 是 v5 sales_v2.py 演示的方向
   - 跟 `sales_v2` 合并是天然顺势

C. **领域服务混合**：聚合根逻辑在 `app/domain/sales/{opportunity,...}.py`，跨聚合的用例在 `app/application/`，单聚合 CRUD 在 services
   - 最"正"
   - 改动最大

### 6.2 前端路由用哪种嵌套方式？

- **方案 X**：`react-router-dom v7` 的 `createBrowserRouter` + `loader/action` 模式
- **方案 Y**：保持当前 `<Routes>` + 自建 `routes/registry.tsx` 元信息

### 6.3 `api/index.ts` 拆分后，是否要按"前后端契约"生成？

- **手工维护**：拆分后人工同步，灵活但易漂移
- **orval / openapi-typescript**：从 FastAPI 自动生成的 OpenAPI 生成前端 client
- **tRPC-style**：后端 Python + 前端 TypeScript 共享 schema 源
